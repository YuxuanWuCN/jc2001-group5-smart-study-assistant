- Functional and Non-Functional Requirements
- Use Cases and Requirements Modelling

2. 遇到的挑战及解决方式；

本周所有任务都必须留下可引用的文件、截图、测试结果或会议记录，避免汇报时只描述结论。

## 2. 第三周结束时的 Definition of Done

周末完成后，以下条件必须全部满足：

- [ ] `reports/technical_report_draft.md` 存在完整的技术报告目录、章节占位、页数配额和图表清单。
- [ ] 第 1 章至少形成一版可审阅正文，并能追溯到 Proposal 的问题、目标、用户和价值描述。
- [ ] 第 2 章具备 FR/NFR 清单、MoSCoW 优先级、验收标准和需求追踪矩阵。
- [ ] 第 3 章具备 8 个核心用例的统一编号、参与者、前置/后置条件、成功流和异常流。
- [ ] 第 4 章具备系统上下文图、用例图、核心时序图、类/领域模型和 Neo4j ontology baseline 的说明。
- [ ] `reports/` 中的 API 映射、图件、用例、RTM、测试计划和实际代码路径名称保持一致；发现的不一致必须登记并处理。
- [ ] reports 至少有一个可演示的查询/报告主流程：选择时间范围或数据范围，查看核心指标和趋势/分布，并显示数据来源或生成时间。
- [ ] reports 相关前后端契约写清楚；若功能仍为 mock，必须明确标注数据来源、限制和替换方式。
- [ ] 题库更新至少有一个可演示闭环：提交题目、校验题目、保存题目、通过 `GET /api/quiz` 读取；无效题目不能进入题库。
- [ ] 题库更新明确题目唯一 ID、学科、题干、至少四个选项、唯一正确答案、解析和陷阱/知识点字段的必填规则。
- [ ] 题库更新至少有 6 个测试/验收记录，覆盖新增成功、重复 ID、缺少正确答案、选项数量不足、读取新题和非法输入。
- [ ] 至少新增或整理 8 个 reports 相关可执行测试/验收记录，覆盖正常、空数据、非法参数和服务失败四类情况。
- [ ] 完成一份 Project Update 1 草稿，包含真实进度、真实风险和下一步，不虚构已完成内容。
- [ ] 完成一次全组 review，确认每位成员的工作记录、提交记录或文档贡献可追踪，为 Appendix A 留证。

“至少一半进度”的本周判定口径：不是按页面数量，而是按技术报告核心链路计数。完成“需求/用例 + 架构/数据 + 实现说明 + 测试证据 + 报告草稿”五个部分中的至少四个，并且 reports 主流程可以演示，视为达到 50% 基线。

## 3. 本周工作流与顺序

### 周一：需求冻结与范围确认

**目标**：确定第三周只交付一个可验证的 reports 主流程，避免继续扩张功能。

交付物：

- `reports/week3_scope_decision.md`
- 更新后的 FR/NFR 与 RTM
- reports 主流程草图（入口、筛选条件、指标、输出、空状态）
- 待向 supervisor 确认的问题清单

必须确认的主流程：

1. 用户进入 Reports；
2. 选择时间范围/学科/数据范围；
3. 系统展示核心指标；
4. 系统展示趋势或分类分布；
5. 用户看到数据来源、生成时间和空数据提示。

建议本周先做学生学习报告，不把教师 cohort heatmap、复杂导出、Neo4j 云端全量同步纳入第三周 Must Have。

### 周二：报告数据契约与题库更新契约

**目标**：把 reports 页面需要的数据和题库更新需要的题目格式定义清楚，避免前后端各写一套字段。

交付物：

- `reports/report_data_contract.md`
- 更新 `reports/api_frontend_mapping.md`
- 明确指标定义、字段类型、单位、时间格式和错误响应
- 一份固定的示例数据集或 mock 数据说明

建议最小指标：

- `attempt_count`：尝试题目数
- `correct_count`：答对数
- `accuracy_rate`：正确率，明确分母为有效提交数
- `diagnostic_count`：触发诊断次数
- `weak_points`：薄弱知识点列表
- `trend`：按日期或按学科的聚合结果
- `source`：数据来源（session/mock/API）
- `generated_at`：报告生成时间

建议接口（最终以代码现状和 supervisor 意见为准）：

- `GET /api/reports/summary`
- `GET /api/reports/trend`

如果后端暂时没有持久化数据，接口必须明确返回 `source: "mock"` 或 `source: "session"`，不能让 mock 数据伪装成真实用户历史。

题库更新的第三周最小契约：

- 输入：`id`、`subject`、`difficulty`、`tag`、`stem`、4 个选项、唯一正确答案、`explanation`；若题目支持智能排雷，再要求陷阱/知识点元数据。
- 校验：ID 必须唯一；学科必须属于现有学科集合；选项数量必须为 4；选项 key 必须唯一；正确答案必须且只能有一个；题干和选项文本不能为空。
- 保存：第三周可以先保存到受控 JSON/内存数据源，但必须说明重启后的持久化行为；不允许直接让前端修改 `seed_questions.py`。
- 发布：只有校验通过的题目才能被 `GET /api/quiz` 返回；失败时返回明确的 4xx 错误，不产生 500。
- 角色：第三周先采用“项目组内部题库维护者”这一单一角色，不新增复杂管理员权限系统；权限和多人并发编辑列入后续确认。

### 周三：Reports 与题库更新最小主流程实现

**目标**：让两个主流程都可以在本地运行并演示，但保持范围可控。

Reports 交付物：

- reports 页面/视图的入口与基本布局
- 时间范围或学科筛选控件
- 指标摘要区域
- 一张趋势或分类分布图
- loading、empty、error 三种状态
- 数据来源和生成时间显示

题库更新交付物：

- 一个题库维护入口，可以是简单表单或受控 JSON 导入，不要求完整后台系统；
- 新题目的字段校验和明确错误提示；
- 新题目保存到受控数据源；
- 刷新/重新请求后，`GET /api/quiz` 能读到新题；
- 至少一条新增题目能实际完成刷题和报告统计流程。

题库更新不纳入本周 Must Have：复杂管理员角色、多人并发编辑、批量 Excel 导入、完整 Neo4j 同步、题目版本回滚。

实现约束：

- 复用现有前端和后端结构，不引入不必要的框架。
- 报告页面只展示已定义指标，不先添加“AI 自动总结”等无法验证的复杂功能。
- 任何指标都必须能追溯到数据字段和计算规则。
- 不把页面数量当成完成度；可演示主流程优先于装饰性 UI。

### 周四：测试、截图与证据整理

**目标**：为 reports 和题库更新的每个可声称结果准备证据。

交付物：

- `reports/reports_test_evidence.md`
- `reports/question_bank_update_evidence.md`
- reports 与题库更新相关测试用例和运行结果
- 桌面和移动视图截图
- reports 的正常、空数据、非法筛选、API 失败结果记录
- 题库更新的成功新增、重复 ID、字段缺失、选项校验、读取新题结果记录
- 性能记录：至少记录一次本地请求耗时和测试环境

最低验收矩阵：

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| RP-01 | 默认范围加载 | 指标、趋势和生成时间正常显示 |
| RP-02 | 切换学科/范围 | 所有显示值随筛选条件一致更新 |
| RP-03 | 无记录 | 显示空状态，不显示误导性的 0% 结论 |
| RP-04 | 非法日期或参数 | 返回可理解的校验错误，不产生 500 |
| RP-05 | API 超时/服务不可用 | 显示错误状态或已声明的 fallback，页面不崩溃 |
| RP-06 | 数据来源检查 | 页面标注 mock/session/API 来源 |
| RP-07 | 移动端查看 | 关键指标和图表不横向溢出 |
| RP-08 | 可访问性基础检查 | 控件可键盘聚焦，关键图表有文字摘要或替代说明 |

### 周五：Technical Report 半程合并

**目标**：把本周实现转换成可直接进入最终技术报告的内容。

交付物：

- `reports/technical_report_draft.md` 更新
- 第 1 章修订稿
- 第 2 章 Requirements 初稿
- 第 3 章 Use Cases and Requirements Modelling 初稿
- 第 4 章 System Design and Architecture 初稿
- 第 5 章 Implementation 中 reports 小节
- 第 6 章 Testing and Evaluation 中 reports 测试小节
- 图表和表格编号清单

每个章节都要包含：

- 内容来源或证据文件；
- 当前状态（draft/verified/needs supervisor confirmation）；
- 与需求、用例、实现和测试的链接。

### 周末：项目更新与全组 review

**目标**：形成真实可提交的 Project Update 1 素材并锁定下周工作。

交付物：

- `reports/project_update_1_draft.md`
- `reports/week3_review_minutes.md`
- 下周任务列表和负责人
- 风险登记表更新

Project Update 1 必须如实写明：

- 已完成：报告结构、reports 主流程、数据契约、测试证据、架构图等；
- 挑战：真实历史数据是否已有、指标定义是否需 supervisor 确认、Neo4j 是否纳入当前 PoC；
- 解决：mock/session 明确标记、统一字段契约、异常状态测试、保留待确认项；
- 下一步：持久化历史数据、补齐报告图件、扩大测试、准备 M2.4 check-in。

## 5. 本周风险与控制措施

| 风险 | 控制措施 |
| --- | --- |
| reports 指标没有真实数据来源 | 先用明确标注的 mock/session 数据；在报告中说明限制和替换方案 |
| 题库更新破坏现有种子题或诊断字段 | 不直接修改 `seed_questions.py`；先做 schema 校验、独立受控数据源和回归测试 |
| 新题目能保存但无法进入刷题/报告链路 | 用一条新增题目跑通保存、`GET /api/quiz`、答题、诊断和 reports 统计闭环 |
| 页面做得很完整但无法证明正确 | 每个指标先写定义和验收标准，再实现和测试 |
| 技术报告内容与代码脱节 | 每个章节绑定代码路径、图件或测试证据 |
| 过度承诺 Neo4j、LLM、云端能力 | 第三周只承诺已运行和可复现的范围，未实现部分列为 future work |
| AI 生成痕迹明显 | 保留真实设计选择、失败记录、测试结果、会议决策和 supervisor 问题 |
| 工作量无法公平核对 | 每周记录负责人、实际投入、交付物和 review 结果 |
| 规格中的数字互相冲突 | 统一性能指标、样本数量、测试数量和数据来源；冲突未确认前不要写成已验证事实 |

## 6. 本周向老师确认的问题

这些问题都直接影响开发范围和验收标准，不是为了凑问题：

1. 第三周 reports 的“完成一半”应按主流程可演示程度、核心接口覆盖率，还是报告章节完成度判断？
2. Reports 第一版是否应优先面向学生个人学习反馈，还是需要同时覆盖教师/管理员视角？
3. 在没有真实历史数据库的情况下，使用明确标注的 mock/session 数据是否可以作为 M2.2 的 PoC 证据？
4. 本周期 reports 是否必须提供持久化历史记录，还是允许先做 session/local 数据，后续再接 Neo4j 或数据库？
5. 最低必须展示哪些指标：正确率、尝试次数、薄弱知识点、趋势，还是老师有指定指标？
6. 题库更新第三周是否只面向项目组内部维护者？是否允许先使用 JSON/内存数据源，后续再接数据库？
7. 新题目是否必须同时填写陷阱、知识点和权威来源，才能进入正式题库？
8. 图表是否需要导出，还是第三周先完成浏览器内查看即可？
7. Technical Report 中的报告截图、测试结果和 mock 数据说明，是否可以先作为 draft，之后随真实数据替换？
8. 当前计划中 Neo4j 和 Qwen 的集成范围是否需要在 M2.2 前完成，还是只需完成 ontology/接口设计并在 M3.x 实现？
9. 老师希望 Project Update 1 重点展示 requirements/architecture，还是希望看到 reports 的实际可运行 demo？
10. 如果部分 NFR（例如真实用户数据安全、持久化可靠性）尚未进入 PoC，是否应明确列为后续阶段而不是本周承诺？
