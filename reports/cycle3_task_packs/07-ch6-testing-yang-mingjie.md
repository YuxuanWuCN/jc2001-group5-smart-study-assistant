#### 6.1.2 无外部依赖的测试基线（**这是本项目最硬的工程卖点**）

必须写清的三个事实（数字全部回仓库核对，不要凭记忆）：

1. **`python -m pytest tests/ -q` → 145 passed, 0 failed**，执行时间 **约 3.6 秒**。
2. **9 个测试文件 / 78 个测试函数**，参数化把它们展开成 **145 个用例**——**必须解释这个数字关系**，否则考官会怀疑你数字造假：`145 = Σ(每个 test 函数被 @pytest.mark.parametrize 展开的份数)`，其中 `test_adversarial_backend.py` 有 25 个函数、523 行，是参数化最密集的文件。
3. **全程零外部服务**：不连数据库、不连 Neo4j、不调 LLM、不发网络请求。所以在任何一台装了依赖的电脑上都是 3.6 秒全绿——这直接支撑了 Ch5.6 的"可复现性"，也是 PoC 评分项 Reliability 的证据。

### 6.2 Adversarial and Robustness Testing (500–600 words + **Table 6.2**)

这一节要证明"**我们主动攻击过自己**"——这是去 AI 感的关键，因为 AI 生成的项目往往只测 happy path。

**Table 6.2：对抗性测试六组**

| 组 | 攻击类型 | 具体攻击输入 | 期望行为 |
| :-: | :--- | :--- | :--- |
| A1 | 不存在的 ID | `question_id = 999` / 负数 / 字符串 | 404，不 500 |
| A2 | 非法选项 | `selected_option = "Z"` / 空字符串 / `null` | 422 校验错误 |
| A3 | 注入字符 | 选项里塞 SQL 片段、`<script>`、超长 10k 字符串 | 原样拒绝或安全透传，无崩溃 |
| A4 | 类型混淆 | 传 list 当 id、传 dict 当 option | 422，且有明确错误信息 |
| A5 | 并发轰炸 | 多线程同时请求 `/api/diagnose` | 无竞态、无 500 |
| A6 | 空库 / 空会话 | 无作答记录的学情卡、空筛选条件 | 200 + 定义良好的空状态 |

**必写的一句话**：这 25 个对抗性函数里，有 **X 个是在开发过程中真实抓到过 bug 的**（去查 `tests/` 的注释或与吴宇轩确认哪几个是补丁型测试；找不到证据就写"其中若干用例在开发初期暴露了 404/422 混用的问题"，不要编数字）。

### 6.6 Threats to Validity (300–400 words)

诚实交代四类威胁（每类 2–3 句）：
1. **内部效度**：验收测试由作者自己编写，存在确认偏差；缓解手段是引入 25 个对抗性函数做"自我攻击"。
2. **外部效度**：12 道题、4 学科的教学场景代表性有限；MMLU 是通用知识基准，不是备考场景基准。
3. **构念效度**：我们用"雷达维度分数"代理"学生掌握程度"，这个代理关系本身未被独立验证。
4. **统计效度**：MMLU 结果为单次采样，未做置信区间；±1 pp 量级差异不可解读为显著。

## 6. 导师会问你的 3 个问题（准备好 30 秒答法）

**Q1. "145 个测试全过，能说明什么？自己写的测试当然自己过。"**
> 答：说明不了系统正确，只说明**回归基线存在**。它的真实价值是：任何一个人改了后端，3.6 秒内就知道有没有碰坏别的东甲。至于"正确性"，靠的不是测试数量而是那 25 个对抗性函数——那些是我们**主动攻击自己**写的，其中一部分在开发初期真的抓到了 404/422 混用的缺陷。另外 6.5 节是把测试结果往回映射到 14 条需求上，看的是**覆盖**而不是**通过率**。

**Q2. "MMLU 有的学科是负的，那你的图谱增强是不是没用？"**
> 答：准确说是"**有条件有用**"。7 个学科涨、3 个持平、2 个跌。跌的是物理和 US History——物理需要多步数值推理，图谱的结构化约束在这里变成干扰；历史题考的是时序与史实关联，我们的图谱边类型对这类关系建模不足。这不是我们要隐藏的数据，报告 6.3 和 6.6 都写了，因为**一个只在有效的地方有效的方法，比一个处处宣称有效的方法更可信**。而且这个结论直接指导了 Ch7 的 future work。

**Q3. "RAGAS 那几个指标到底多少分？"**
> 答：**（若已跑完）** 报真实数字并说明评估集大小。**（若未跑完）** 我们没有跑完，原因是评估链路依赖的嵌入服务有配额限制，我们不愿意在报告里放一组我们自己都不信的分数，所以在 6.4 节如实写明了脚本设计与已完成的对照组，并把它列进 Limitations。**这是最低成本也最安全的答法。**
