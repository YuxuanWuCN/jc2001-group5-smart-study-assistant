## 2. 逐节结构与字数预算

### 5.5.1 Design Principles (300–400 words)

先立三条原则，后文每条都回来呼应（这是本章的骨架）：

| 原则 | 教学目的 | 视觉落点 |
| :--- | :--- | :--- |
| **P1 · 答案永不先于思考**（Answer Never Spoils） | 学生必须先选再看到解析，否则学习无效 | 正确答案与 `explanation` 默认折叠，提交后才展开 |
| **P2 · 诊断渐进披露**（Progressive Disclosure of Diagnosis） | 一次给五层信息会把人淹死 | Trap Drawer 五层，一层一句，可展开可收起 |
| **P3 · 数据先于装饰**（Data over Decoration） | 学生要的是"我现在弱在哪"，不是氛围 | 雷达图占据主视觉；无装饰性动画阻塞信息 |

**必须写清 P1 的由来**：这是我们在 Ch1 里批判的"通用 LLM 的 Answer Spoiling 问题"的界面级对策——**同一个洞察在 Ch1 是问题陈述，在这里是设计约束，前后呼应极强。** 这句要写出来。

### 5.5.2 Interface Architecture (300–400 words)

写清**为什么界面是零构建的**（但**不要重复江昊 5.1 的技术论证**，只写"这对界面设计意味着什么"）：

- 没有组件库 → 所有视觉组件手写 CSS（`style.css` 73 KB），因此视觉语言完全自定义，不会撞上 Tailwind 默认样式；
- 没有构建步骤 → 改一行 CSS 保存即生效，**设计迭代周期从"改-编译-刷新"降到"改-刷新"**，这是我们能在同一周期内把界面打磨到这个程度的原因；
- 单文件 `app.js`（259 KB）→ 所有交互逻辑集中，**状态切换点可见**（例如答题态 / 诊断态 / 报告态的切换都集中在事件总线里），减少了"状态散落在多组件里"的不一致 bug。

**一句话总括**（可作为小标题下第一句）：
> 零构建在这里不是性能噱头，而是**设计迭代速度的来源**——它让我们能在两周内把界面从能用到可讲。

### 5.5.3 The Trap Drawer: Core Interaction (500–600 words + **Figure 5.3**)

**本节的灵魂。** 截一张真实的错答后展开的 Trap Drawer（**必须标注真实 commit hash 与截图日期**，例如 "Screenshot taken from commit `09ae770`"）。

五层结构与 `TrapDetail` 的映射（**必须与董思钦 5.3 的字段名逐字一致**）：

| 层 | 界面显示 | 数据来源 | 教学意图 |
| :-: | :--- | :--- | :--- |
| 1 | 你选择了 B —— ✗ | `selected_option` | 制造认知冲突（先确认事实） |
| 2 | **误区命名**：把撤销权除斥期间当作诉讼时效 | `TrapDetail.title` | 给误解一个可记忆的标签 |
| 3 | **错在哪**：…… | `TrapDetail.desc` | 解释，而非只判错 |
| 4 | **你缺的前置知识**：…… | `TrapDetail.prereq` | 把"错"转成"该补什么"（可执行） |
| 5 | **正确解析**（含权威出处） | `QuizItem.explanation` | 兜底正确知识，附法条/公式来源 |

**必须写的一段对比**（这段是你这一节的技术含量所在）：
> 传统题库的反馈是**一个布尔值**（对/错）加上一段通用解析；我们的反馈是**一个五层结构**，其中第 3、4 层是针对**这个具体错项**的，而不是针对这道题的。第 4 层（前置知识）是我们认为最有价值的一层：它把"你错了"翻译成"你该去补哪一块"，这是一个学生可以立刻行动的信息。

**再补一个交互细节**（体现你真的做过）：为什么是抽屉（drawer）而不是模态框（modal）？答：模态框会遮住题目，学生无法对照题目与诊断；抽屉从右侧滑出只覆盖 40% 宽度，题目保持可见——**这就是"诊断必须能对照原题看"这个教学需求决定的视觉形态。**

## 6. 导师会问你的 3 个问题（准备好 30 秒答法）

**Q1. "这个界面是你设计的，还是 AI 生成的？"**
> 答：界面是手写 CSS（73 KB，无组件库、无 Tailwind），所有视觉决策都能追溯到具体约束——比如为什么 Trap Drawer 是右侧抽屉而不是弹窗，是因为弹窗会盖住题目，学生没法对照原题看诊断；比如为什么正确答案默认折叠，是因为我们 Ch1 批判的 Answer Spoiling 问题必须在界面层被解决，而不只是写在报告里。**如果您想验证，我可以现场改一行 CSS，保存后刷新就生效——因为整个前端没有构建步骤。**

**Q2. "界面做得这么精致，是不是把精力放错地方了？"**
> 答：界面分的是 30% 里的 UI-UX 项，不是装饰。而且我们的"精致"集中在**信息组织**上（五层诊断、雷达维度、空状态），而不是动画和插图上。如果您看截图会发现几乎没有任何装饰性动画——因为 P3 原则是"数据先于装饰"，一个学生打开页面应该 3 秒内看到"我弱在哪"，而不是看一个渐变进场动画。

**Q3. "后端挂了会怎样？"**
> 答：因为前端静态资源是由同一个 uvicorn 进程通过 `StaticFiles` 提供，所以后端彻底挂了页面也打不开——这是单进程架构的固有代价，ADR-01 里写明了。但这个"挂"在实践中的形态是 API 请求失败而不是整站白屏：如果只是某个 API 出错（比如 500），前端会捕获并展示可读的错误提示，不会把 `undefined` 渲染到界面上。**离线场景下整个应用仍然可用是设计目标，而不是"断网也能部分可用"。**
