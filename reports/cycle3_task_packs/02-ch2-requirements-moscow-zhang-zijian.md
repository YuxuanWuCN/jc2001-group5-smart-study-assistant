官方 Brief 要求本章覆盖 **usability / performance / reliability / security / maintainability** 五类 NFR——这是硬性要求，五类一个都不能少。

### 2.1 Requirements Elicitation (500–600 words)

#### 2.1.1 我们怎么得到这些需求（**必须诚实**）

写清四条来源，每条都要可验证：

| 来源 | 我们做了什么 | 产出 |
| :--- | :--- | :--- |
| **文献与既有研究** | 阅读 spaced repetition、intelligent tutoring system、knowledge tracing 相关文献 | 教学法约束（反馈必须细粒度） |
| **竞品分析** | 分析 Quizlet / Anki / Khanmigo / ChatGPT / Chegg（详见 `reports/competitor_analysis.md`） | 竞品功能矩阵、差异化定位（Ch1 Table 1.1） |
| **团队内部需求工作坊** | 组内 10 人对"学生备考真实痛点"做结构化讨论与投票 | Persona 候选、功能优先级初稿 |
| **前序周期实证** | 前一周期的进度报告与 MMLU 对照实验 | 技术可行性的实际边界（决定了哪些功能可做） |

> 🔴 **学术诚信红线**：**绝不虚构"我们做了 n=200 的学生问卷"**。如果没做正式问卷，就在 2.1.3 明确写"本研究未进行大规模用户调研，需求来源为文献、竞品分析与团队内部工作坊——这是本报告 Limitations 中的一条"。**编造调研数据一旦被发现，整份报告的可信度归零。**

#### 2.1.2 Functional 与 Non-Functional 的划分依据

写清你用的是什么标准（例如 IEEE 29148 风格的区分：functional = 系统做什么，non-functional = 做得怎么样）。**引用一个标准比自创分类更专业。**

#### 2.1.3 Elicitation Limitations（必写，150–200 词）

诚实交代三件事：
1. 未做规模化用户访谈/问卷（原因：课程周期与资源限制）；
2. Persona 基于文献与竞品行为推断，而非实测用户画像；
3. 需求优先级由团队判断，未经真实用户加权验证。

**然后转折一句**（这才是成熟写法）：
> 这些局限不改变本项目的可行性结论，但意味着我们的需求清单应被视为**一组有据可依的假设（informed hypotheses）**，而非经过验证的用户事实。我们把它们逐条列为可被 Ch6 检验的命题，而不是既成事实。

### 2.3 Non-Functional Requirements (**Table 2.3，官方五类强制**)

**Table 2.3：五类 NFR 规格**（每一行必须可度量）

| 类别 | 编号 | 要求（写成可测的阈值） | 如何验证 |
| :--- | :-: | :--- | :--- |
| **Usability** | NFR-U1 | 新用户无需文档即可完成一次答题；主流程 ≤3 次点击 | 可用性走查 + 视频演示 |
| **Usability** | NFR-U2 | 中英双语、明暗双主题，文字对比度 ≥ WCAG AA（4.5:1） | 对比度检查工具截图 |
| **Performance** | NFR-P1 | 任一 API 响应 P95 < 100 ms（本机、无并发） | `test_empirical_stress.py` 实测 |
| **Performance** | NFR-P2 | 首屏 FCP < 100 ms（本地静态资源，无外部请求） | 浏览器 DevTools 实测截图 |
| **Reliability** | NFR-R1 | 演示路径零外部依赖：无数据库、无 LLM API、无云服务 | 断网启动实测 |
| **Reliability** | NFR-R2 | 全部非法输入返回 404/422/409 等分类错误，**不返回 500** | 25 个对抗性用例 |
| **Security** | NFR-S1 | 所有输入经 Pydantic 校验；无 SQL/命令拼接面 | 代码走查 + 注入类用例 |
| **Security** | NFR-S2 | 仓库与交付 ZIP 中**不含明文凭证** | 提交前全仓搜索（**已知历史泄露项，见 5.6.5**） |
| **Maintainability** | NFR-M1 | 分层结构（router / service / model / data），service 层可脱 HTTP 单测 | 目录走查 |
| **Maintainability** | NFR-M2 | 回归网 ≥140 个自动化用例，全绿执行 < 10 s | `pytest -q` 实测 145 passed / 3.6 s |

**写作要求**：
- **每一条都要有阈值或验证方式**，没有阈值的 NFR 等于没写；
- **Security 那两行是本项目的真实弱项**（ADR-06 的 CORS 通配、ADR-07 无真正鉴权、以及一次历史凭证泄露）——**在这一章就诚实列出，不要等考官发现**。NFR-S2 的"已知历史泄露项"就是为了让这条不显得像事后补的。

### 2.4 Lean Scoping: What We Deliberately Cut (600–700 words)

**这是全章最有价值的一节，也是"初创叙事"的核心。**

写法：每条 Won't 都用三段结构——**(a) 它是什么 (b) 为什么诱惑我们 (c) 我们为什么砍掉**。

#### R11 多用户 / 多租户隔离
- (a) 教师端班级管理、学生数据隔离、权限体系；
- (b) **它是最明显的"专业性信号"**：有登录、有角色、有权限，看起来就像真产品；
- (c) **砍掉的理由**：多租户一旦进来就要数据库、要迁移、要鉴权中间件、要数据隔离测试，保守估计 3 周工作量——而它对本项目的**核心论点（选项级诊断是否可行）一点贡献都没有**。我们保留了登录（因为它让演示更完整），但不做多用户数据隔离。这是**"保留信号、砍掉成本"**的典型裁剪。

#### R12 移动原生 App
- (c) 理由：单一 Web 响应式界面已覆盖手机浏览器；原生 App 需要第二套技术栈与发布流程，投入产出比在本周期内为负。

#### R13 社交功能（排行榜 / 分享）
- (b) **它是最强的"增长叙事"**：排行榜天然带病毒传播；
- (c) 理由：排行榜会引入**与教学目标相反的动机**——学生为排名刷题而不是为掌握知识点做题。我们在 Ch5.5 的界面原则里明确写了这一点（P3 数据先于装饰）。**这不是做不出来，是不该做。**

#### R14 自动组卷 / 自适应出题
- (b) 它有学术性感：IRT / CAT / BKT 都能用上；
- (c) 理由：自适应出题的前提是**足够大的题库**（通常 ≥200 题才能做能力估计），我们只有 12 题——做了也只能是假的。**声称做了自适应但我们只有 12 道题，是最容易被当面问穿的那种"AI 式宏大叙事"。**

**然后用一段话把这一节升维**（能显著提升评分）：
> 一份需求文档的成熟度，不在于它列了多少功能，而在于它**敢不敢写 Won't**。我们砍掉的四条功能，每一条单独看都像"应该做"的功能；把它们放在一起看，会发现它们共享同一个特征——**它们都在增加交付成本，却不推进本项目的核心论点**。这份报告要说清的是"选项级诊断这条路可行"，而不是"我们能做出一个教育平台"。

## 6. 导师会问你的 3 个问题（准备好 30 秒答法）

**Q1. "这四条 Won't 是真的做不出来，还是懒得做？"**
> 答：**R11 多租户是做得出但不该现在做**——它需要数据库、鉴权中间件、数据隔离测试，约 3 周，对"选项级诊断是否可行"这个核心论点零贡献；**R14 自适应出题是 12 道题根本支撑不了的**，声称做了反而是虚假叙事；**R12 移动原生是投入产出比为负**；**R13 排行榜是不该做，不是做不出**——它会让学生为排名刷题而不是为掌握知识做题，这与我们的教学目标直接冲突。这四条理由都在 2.4 里写清了，一条没藏。

**Q2. "你们做过用户调研吗？这些需求凭什么说是学生想要的？"**
> 答：**没有做大规模调研，这一点我们在 2.1.3 明确写了。** 需求来源是文献、竞品分析和组内工作坊，所以我们在报告里把它定位为"有据可依的假设"而不是"已验证的用户事实"。我们认为把没做的调研说成做了，比承认没做更危险——因为考官只要问一句"问卷在哪"就会崩。

**Q3. "14 条需求，你们真的有把握逐条验收？"**
> 答：有，而且已经做了。**R10 是唯一一条我们标"部分满足"的**——它只有离线评估证据、没有在线链路证据。这一条在 Ch6.5 的需求逐条评估表里会明确标出来，在 Ch7 的 Limitations 里也会再出现一次。**我们宁可让一条需求显示未完全达成，也不把它写成"已实现"。**
